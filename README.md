# Ludo Arena

A responsive Ludo game built with React, Vite, Tailwind CSS, Firebase Authentication, Firestore, Cloud Functions, and Lucide icons.

## What works

- **Local practice:** pass-and-play for 2–4 people on one device; no login or internet match is implied.
- **Multiplayer:** private six-character rooms, 2–4 authenticated players, ready checks, live Firestore updates, connection heartbeats/reconnection, and server-validated game actions.
- **Rules:** four tokens per player, six to leave base, clockwise movement, six grants another roll, captures send opponent tokens to base except on safe squares, exact roll to finish, and winner detection.
- **Accounts:** Google and email/password sign-in, Firebase profile records, match history, verified multiplayer win/loss counts, and a wins leaderboard.
- **Game controls:** sound toggle, game instructions, exit and rematch actions.

Multiplayer is intentionally unavailable until Firebase has been configured and the Cloud Functions and rules have been deployed. The app does not simulate remote players or claim an untested online connection.

## Requirements

- Node.js 20.19+ or 22.12+
- npm
- A Firebase project with Authentication, Cloud Firestore, Cloud Functions, and Firebase Hosting enabled
- A Firebase **Blaze** billing plan for Cloud Functions and the scheduled connection-presence cleanup

## Local development

1. Install frontend dependencies:

   ```sh
   npm install
   ```

2. Copy `.env.example` to `.env` and add the Firebase web app configuration values. These are Firebase client configuration values, not service-account credentials.

3. Run the website:

   ```sh
   npm run dev
   ```

   Without a configured Firebase app, the local practice game and its rules remain available. Authentication and online rooms show a configuration message instead of falling back to fake multiplayer.

4. Run the rules-engine tests and production build:

   ```sh
   npm test
   npm run build
   ```

## Firebase setup and deployment

1. Create a Firebase project and register a Web App. Put its web configuration in `.env` using the variable names from `.env.example`.
2. In Firebase Console → Authentication → Sign-in method, enable **Email/Password** and **Google**. Add your local and deployed domains to authorized domains.
3. Create the Cloud Firestore database.
4. Install the Firebase CLI if needed and authenticate:

   ```sh
   npm install -g firebase-tools
   firebase login
   firebase use YOUR_FIREBASE_PROJECT_ID
   ```

5. Install the Cloud Functions dependencies and deploy backend controls:

   ```sh
   npm --prefix functions install
   npm run deploy:rules
   npm run deploy:functions
   ```

6. Build and deploy the frontend to Firebase Hosting:

   ```sh
   npm run build
   firebase deploy --only hosting
   ```

   Or deploy the configured Hosting, Firestore rules/indexes, and Functions together with `firebase deploy`.

The Cloud Functions use Firebase Admin credentials supplied by the deployed Firebase runtime; do not create or commit a service-account key. Callable functions enforce membership, room capacity, readiness, current-turn ownership, legal token movement, and server-side dice rolls within Firestore transactions. Client writes to rooms are denied by [firestore.rules](./firestore.rules).

## Data model

- `rooms/{roomId}` — private room, players, connection timestamps, and authoritative game state. Only room members may read; all client writes are denied.
- `roomCodes/{code}` — server-only room code lookup.
- `profiles/{uid}` — player identity and multiplayer aggregate stats. A signed-in owner can update identity fields, but cannot change stats.
- `profiles/{uid}/matches/{matchId}` — server-written match history; readable by the profile owner only.

The scheduled `expirePresence` function marks players offline after 90 seconds without a heartbeat. Rejoining a room with the same account reconnects an existing seat, including an in-progress game. Firestore updates are real-time for room members.

## Notes

- Client-side Firebase web configuration is public by design; access control comes from Firestore rules and callable-function validation. Never put Admin SDK credentials in `VITE_*` variables.
- The leaderboard and match history count completed **online** matches only. Local practice is not stored as multiplayer history.
- Sound is generated with the browser Web Audio API and can be disabled in the game screen.
- The dice values are generated by Cloud Functions for online games. Local practice dice are generated in the browser.
